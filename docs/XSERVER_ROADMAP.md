# Xserver本番移行・業務改善ロードマップ

更新：2026-11-13  
目的：単なる帳票作成サイトではなく、**学校への教材提案・見積・受注・メーカー発注・出荷・納品・請求・回収までを、担当営業と本部が安全に共有する業務基盤**を作る。

この文書の**提案中**の内容は未承認であり、画面や機能を勝手に変更しない。最終仕様は [CURRENT_SPEC.md](./CURRENT_SPEC.md) の最新決定に従う。

## 環境を分ける

| 環境 | 用途 | 扱えるデータ | 公開・運用 |
|---|---|---|---|
| GitHub Pages（現在） | 見た目と操作の試作、検証 | **架空データのみ** | 公開される前提 |
| Xserver ステージング（提案） | 本番に近い表示・認証・保存・印刷・復元の確認 | 検証用データのみを原則 | アクセス制限が必要 |
| Xserver 本番 | 正式な注文・見積・社内業務 | 承認された必要最小限の情報 | HTTPS＋ログイン・権限制御・監査・バックアップ |

GitHub PagesのHTMLを単純にコピーしても、**社員専用の安全な業務システムにはならない**。本番の認証・権限・データ保存・バックアップ・監査を実装し、実務テスト後に移行する。

## 業務の全体像

1. 学校からの依頼を取り込む：学校向けWeb／FAX／電話／訪問。重複受付を検出し、担当営業を関連付ける。
2. 案件作成・見積：学校マスター、発注先マスター、品番、明細、学年組別数量。見積番号を付番し、校内承認用の印刷にも対応。
3. 注文確定：見積から注文へ内容を引き継ぐ。ただし**見積番号と注文番号は別**。履歴に元の見積を残し、注文後の誤操作・二重送信を防ぐ。
4. タナカ本部／担当営業：受注状況を確認し、必要な確認や返信を行う。注文の行方が追えるようにする。
5. メーカー発注：発注先別の発注書を作成・確認し、正式送信前のチェックを設ける。
6. **出荷情報の入力**：FAX・メール・電話で届く情報は、手動入力を基本に設計。部分出荷・欠品・納期変更を記録。
7. 納品書：出荷情報・受注明細から下書きを生成し、まとめる／分ける／追加／修正できる。
8. 請求書：納品内容から作成し、請求先・金額・税・まとめ／分割・訂正履歴を管理する。
9. 回収・締め処理：銀行振込・担当営業集金などを追跡。入金消込や支払条件は別途決定する。
10. 一括管理：案件に見積書・注文控え・発注書・出荷履歴・納品書・請求書・対応履歴を関連付ける。検索・印刷・再発行・集計に対応。

## 本番の安全設計：実装前に協議・確認する項目

| 項目 | 最低限の方針 | 状態 |
|---|---|---|
| 認証 | 社員ごとのログイン、セッション有効期限、パスワードの安全な保存、可能なら多要素認証 | 提案 |
| 権限 | 本部：全件、営業：割当案件中心。画面だけでなく**サーバー側でも**権限を検査 | 提案 |
| データベース | 学校・発注先・担当者・案件・明細・出荷・帳票の関係を整理し、変更履歴・版管理を残す | 提案 |
| Web対策 | HTTPS、WAF、CSRF対策、入力検証、出力エスケープ、SQLパラメータ化、アップロード制限、レート制限 | 提案 |
| 二重注文防止 | 注文確定は一意キー等で一回だけ処理し、受付番号・完了結果を記録。再送・画面戻り・通信断を検証 | 提案 |
| 共用PC対策 | 自動ログアウト、キャッシュ制御、個人情報を端末に残さない設計、ファイル保存時の案内 | 提案 |
| ファイル | 帳票・注文書・PDFを一般公開領域に置かず、認証済みの利用者だけ取得できる仕組み | 提案 |
| 通知 | 学校・営業・本部へ必要最小限の通知。メール本文に詳細な注文／個人情報を不用意に含めない | 提案 |
| バックアップ | DB・添付ファイル・設定を対象に、**復元試験まで**実施。Xserverのバックアップだけに依存しない | 提案 |
| 監査 | 受付、編集、送信、取り消し、帳票発行の実行者・日時・変更内容を追えるようにする | 提案 |
| リリース | ステージング→テスト→承認→本番、ロールバックと緊急停止の手順を用意 | 提案 |

Xserverの機能・契約プラン・PHP／DB構成・WAF設定・バックアップ条件などは、実装時に**管理画面と公式仕様で現物確認する**。未確認の提供機能を「使用可能」「安全」と断言しない。

## 業務改善アイデアの蓄積（確定仕様ではない）

| 課題 | 根本提案 | 期待する改善 |
|---|---|---|
| 同じ学校・メーカー情報を繰り返し入力 | 共有マスターと変更履歴、重複候補の確認 | 入力時間と宛先誤記を削減 |
| FAX・電話注文が紙で散在 | 受付一元化と添付の紐付け、担当・進捗の可視化 | 漏れ・重複を防止 |
| 見積後の正式発注で再入力 | 見積→注文の複製と**独立番号**・差分履歴 | 入力負担と数量ミスの低減 |
| 出荷が分割・欠品になる | 商品行単位で「受注数／発注数／出荷数／残数」を管理 | 納品書・請求書の誤作成防止 |
| 納品書と請求書を都度作り直す | 出荷・納品の確定情報から原案作成、手直しの履歴を保持 | 作業削減と追跡性向上 |
| 問い合わせが担当者しか分からない | 案件ごとの対応履歴・次回確認日・通知 | 本部との共有、引継ぎ円滑化 |

新しい課題が出たら、まず「症状・原因候補・影響範囲・暫定回避策・根本案・承認要否・検証方法」を記録する。改善が決定したときだけ [CURRENT_SPEC.md](./CURRENT_SPEC.md) の有効仕様に昇格させる。
