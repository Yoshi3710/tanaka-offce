# 担当営業の「自分の仕事」中心の画面・権限設計（案 v0.1）

作成：2026-11-13  
状態：**提案中・未承認・未実装**（基本方針のみユーザー決定済み）  
参照：[最新決定事項](./CURRENT_SPEC.md)／[データ設計](./DATA_MODEL_DRAFT.md)

## 変更しない最優先の基本方針

**営業担当者が、自分の担当校・案件・その日の必要作業だけを迷わず確認・処理できることを最優先する。** 本部用の全件管理画面を営業へそのまま流用しない。社内ID、見積番号、注文番号は用途を分け、画面に不要な技術情報を出さない。

## 担当営業の入口（表示案）

| 表示順 | 内容 | 操作イメージ |
|---|---|---|
| 1 | **自分の今日の作業**：学校への返信待ち、見積作成、注文確認、納期確認、納品・請求の要対応 | 1件を押せば該当案件・該当作業へ直接移動 |
| 2 | **自分の担当校**：学校名・電話・住所・最近の案件 | 学校を選ぶだけで新規受付・見積・注文に進める |
| 3 | **自分の案件**：未処理を先頭に並べ、状況で絞り込み | 状況・担当・期日・次の操作を同じ行に表示 |
| 4 | **手動受付**：FAX／電話／訪問。必要最小限を先に入力 | 不明な明細は「要確認」の下書きとして仮受付 |
| 5 | **最近使った学校・発注先・帳票** | 同じ情報の再入力を減らす |

操作はPCとスマホに対応し、入力途中の画面切替・通信断による作業消失を防ぐ。長文・文字・数量・日付は枠内からはみ出さない。全件閲覧・一括管理・設定等の本部機能は別の入口とし、営業画面を複雑にしない。

## 最小の入力で業務を完了するための提案

- **学校マスター選択** → 学校住所・電話・担当営業を必要に応じて補完。似た名前は候補として確認させる。学校の「ご担当者」は変更があり得るので別管理。
- **見積から注文へ** → 商品、単価、学年・組の内訳をコピーし、注文として最終確認。番号は見積と注文で別。
- **注文からメーカー発注へ** → 対象メーカーを選び明細を抽出。仕入単価は必要な権限のある者だけ表示。送信前に数量・学校・宛先を確認。
- **メーカー出荷連絡** → 電話・FAX・メールからの数量・日付を手動で簡潔に登録。「全数／一部／欠品」を選択し、残数を自動計算。
- **納品・請求** → 出荷実績をもとに下書きを生成。営業の入力は不足事項だけに絞り、最終処理は本部と役割を調整。

## 「見える範囲」と「できる操作」を分ける（提案）

| 画面・操作 | 担当営業 | 本部 | 例外 |
|---|---|---|---|
| 担当校一覧・電話・住所 | **自分に割当のある学校** | 全学校 | 正式な代理・引継ぎ時のみ期限付き共有 |
| 案件・明細・対応履歴 | **自分の案件** | 全案件 | 共同担当や引継ぎを明示登録 |
| 新規受付・下書き見積 | 自分の担当校・案件 | 全案件 | 未割当学校の受付は一時受付箱→本部割当 |
| 正式受注確定 | **権限は要決定** | 権限付与者 | 二重確定防止・操作履歴を必須 |
| メーカー発注の正式送信 | **権限は要決定** | 権限付与者 | 誤発注防止の確認工程 |
| 出荷情報の登録 | 自分の担当案件の範囲（案） | 全案件 | 本部入力も可、入力者を記録 |
| 納品・請求書の発行 | **権限は要決定** | 権限付与者 | 閲覧と発行は別権限 |
| 全体売上・仕入単価・他営業案件 | 原則表示しない | 権限による | 役員「社長」の扱いは**別途確認** |

「自分の担当だけ」は**画面上のセレクトボックスで絞ることではない**。Xserver本番では、ログイン中の利用者IDをサーバーが確認し、一覧・個別閲覧・保存・変更・帳票ダウンロード・集計・検索・通知のすべてを同じ権限で制限する。URLを直接入力、リクエストの担当IDを改変、JSONに他担当IDを入れるなどの操作でも、担当外情報を取得できない必要がある。

## 提案するデータの持ち方

- `school_assignments`：学校ID、担当営業ID、開始／終了、主担当／補助担当、登録者、変更理由。学校単位の担当を明確化。
- `case_assignments`：案件ID、担当営業ID、主担当／補助担当、有効期間。学校の担当変更があっても進行中の案件の責任が消えない。
- `case_tasks`：案件ID、作業種別（見積作成・返信・発注確認・納期回答・納品・請求など）、責任者、期限、状態、優先度。**今日の仕事一覧**の基礎。
- `case_access_grants`：一時的な代理・引継ぎの許可、許可者、期間、理由。恒久的な全件公開にしない。
- `audit_events`：変更・確定・発行・代理閲覧の記録。権限を持つ人のみ参照可能。
- 学校や発注先のマスター自体は一元管理しても、**検索候補・件数・帳票・集計**で他担当の情報が漏れないようにする。

## 業務上の確認ポイント（未確定）

| ID | 決める内容 |
|---|---|
| SALES-01 | 主担当の割当単位は「学校」か、「学校＋案件」か。学校変更時の未完了案件の引継ぎ方法 |
| SALES-02 | 社長は「営業担当の1人」として自分の案件だけ表示するか、本部同様に全件を見るか |
| SALES-03 | 受付・見積・メーカー発注・請求のうち、どの確定処理を営業に許可するか |
| SALES-04 | 本部代理受付時の担当営業への通知と、その返信期限 |
| SALES-05 | 担当外学校への新規問い合わせ、代理不在、共同担当の扱い |
| SALES-06 | スマホで特に頻繁に使う操作・並び順・画面遷移 |

## 将来の検証条件

1. 営業「大田」でログイン→大田の学校・案件・タスクのみ表示。**他の営業分の件数も漏らさない**。
2. 大田が「恩田」の案件IDをURL指定しても、API・PDF・検索・エクスポート・更新でアクセス拒否。
3. 正式な代理権限を与えた場合のみ対象案件が見え、期限切れで自動的に見えなくなる。
4. 本部は全件一覧を見られ、担当・期日・処理状況で絞れる。
5. 画面切替・更新・スマホ操作で入力中データが意図せず消えない。
6. 通知・履歴・CSV/PDFに担当外の情報が混ざらない。
7. 担当変更をしても、変更前に確定した帳票の内容と履歴が保持される。
8. 画面の主要操作（担当校→案件→必要な作業）を、実際の営業担当者がPCとスマホで使えるか確認する。

**注意：** 現行の公開 `staff.html` の「担当営業」セレクトは**表示用の試作**であり、認証や担当者制限ではありません。現時点で実運用の安全性は確認されていません。画面を変更する際には、ユーザーの指示と既存デザイン保持の原則に従う。
