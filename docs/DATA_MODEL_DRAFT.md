# フェーズB：受発注データ設計（案 v0.1）

作成日：2026-11-13　／　状態：**提案中・未承認・未実装**  
適用予定：社員用受発注管理の Xserver ステージング／本番。GitHub Pages の試作画面は変更しない。

**最優先の参照先：** [最新決定事項](./CURRENT_SPEC.md)。ここで提案する項目は、承認されるまで確定仕様ではない。

## 目的と大原則

受付・見積・正式注文・メーカー発注・出荷情報・納品書・請求書・入金までを**同じ案件の下で関連付け、内容を再入力せずに引き継ぐ**。ただし一度確定した帳票・金額は、元データの後日修正で勝手に書き換わらないようにする。

- **学校の見積番号と注文番号は別。** メーカー宛発注書番号、納品書番号、請求書番号も別。社内の技術的なUUIDは表に出す「管理番号」と混同しない。
- 教員・担当営業・学校・発注先・帳票に必要な項目だけ扱う。**児童生徒の個人情報は原則取得しない**。
- 電話・FAX・訪問・Webのどれから来た依頼でも受付可能。添付ファイルを安全に保存する方法は本番側で検討。
- メーカーの出荷連絡は**手入力が多い**。出荷記録から納品書の下書きを生成し、納品書そのものは手直し・まとめ・分割可能とする。
- 金額は**学校向け販売単価**と**メーカーからの購入単価**を区別。数量は学年・組の内訳、メーカー発注数、出荷数、納品数を別々に記録。
- 受付・発注確定・出荷・請求などの重要操作は、編集可能な下書きと**確定済みの記録**を明確に区別する。

## 予定テーブルと主な項目

| テーブル（候補名） | 主要項目（例） | 役割・制約 |
|---|---|---|
| \`users\`／\`roles\` | 社員ID、氏名、営業担当、権限、利用可否 | 本部／営業の権限をサーバー側で判定 |
| \`schools\` | 学校ID、学校名、住所・郵便番号、TEL、状態 | 学校名は重複し得るので名前だけで自動確定しない |
| \`school_contacts\` | 学校ID、教員名（必要時のみ）、連絡先、在籍年度 | 担当者変更を学校マスター本体と分離 |
| \`suppliers\` | 発注先ID、名称、住所、電話、FAX、取引先コード、状態 | 発注書用。メーカー名の似た登録を確認 |
| \`cases\` | **社内ID（UUID）**、学校ID、営業ID、受付経路、受付日時、状況 | 1案件は複数の見積・注文・発注に関連し得る |
| \`case_notes\`／\`activity_logs\` | 案件ID、記録日時、操作者、対応区分、内容 | 学校・メーカーへの連絡を時系列に記録 |
| \`quotes\`／\`quote_lines\` | 見積番号（外部表示）、版、期限、明細、数量、学校向け単価、税率、確定時点の宛先写し | 元の品番・学校マスター変更でも確定見積は保持 |
| \`orders\`／\`order_lines\` | 注文番号（外部表示）、依頼経路、見積への参照、学校確認日時、商品行、学校向け単価、確定時点の宛先写し | 見積から引き継ぐときは**コピー＋参照**。学校注文の確定は一度だけ |
| \`class_allocations\` | 注文明細ID、学年、組、数量 | 同商品を複数学年・組へ分ける。内訳合計と注文明細数量を照合 |
| \`purchase_orders\`／\`purchase_order_lines\` | メーカー宛発注書番号、発注先ID、関連注文明細、発注数量、仕入単価、送信状態、宛先写し | 学校への販売単価とは分離。複数メーカーへ分けられる |
| \`shipments\`／\`shipment_lines\` | 出荷連絡ID、メーカー発注行ID、出荷数量、出荷日、見込み納品日、連絡経路、入力者 | FAX・メール・電話での手動登録を想定。分納・欠品・訂正履歴が必要 |
| \`delivery_notes\`／\`delivery_note_lines\` | 納品書番号、宛先写し、明細、数量、作成／確定日時 | 出荷記録から下書き作成。分割・統合・修正可 |
| \`delivery_sources\` | 納品書明細ID、出荷明細ID、割当数量 | どの出荷からどれだけ納品書に記載したかを追跡 |
| \`invoices\`／\`invoice_lines\` | 請求書番号、請求先写し、品目、数量、税区分、合計、確定日時 | 納品に基づいて生成。割当・修正理由を保持 |
| \`invoice_sources\` | 請求書明細ID、納品書明細ID、割当数量 | 請求の重複・欠落を確認。まとめ請求、分割請求に対応 |
| \`payments\`／\`payment_allocations\` | 入金ID、入金日、金額、方法、請求書への消込額 | 銀行振込・担当営業集金等。現金管理の詳細は別途確認 |
| \`document_versions\` | 帳票種別、帳票ID、版、発行日時、作成者、状態、保存場所、ハッシュ | 編集・再発行の履歴。PDFなどは認証後のみ取得 |
| \`operation_requests\`／\`audit_events\` | 操作識別キー、操作者、対象、受付結果、日時、前後の差分 | **二重送信防止**と追跡に使用。個人情報のログ記載は最小限 |

### 重要なデータの区別

- **案件ID（内部 UUID）**：全工程を内部で結び付けるキー。学校に発行する「管理番号」ではない。
- **見積番号・注文番号**：それぞれ独立して発行し、公開帳票に表示。空番や採番ルール、枝番・改訂版は今後確認。
- **仕入先発注書番号**：メーカー宛の送付書類に表示する番号。学校の注文番号とは別。
- **スナップショット**：帳票確定時の学校名・学校住所・発注先名称・数量・価格・税率などをコピー保持し、マスター更新で過去帳票を変えない。
- **版管理**：下書きは修正可能、発行済みは保存。訂正は新しい版または取消記録を作る。元の確定記録を上書きして痕跡を消さない。

## 受注・出荷・請求の不整合を防ぐ設計

| 問題 | 実装時の対策案 | 確認すべきテスト |
|---|---|---|
| 同一注文を二度送信 | 注文確定要求に**一意な冪等キー**。DBトランザクションと一意制約で再送時も同じ結果を返す | 連打・通信切断・ブラウザ戻る・再送 |
| 同一学校の名前違い登録 | 郵便番号・住所・学校コード等で**重複候補**を出す。自動合併せず人が確認 | 同名学校・改称・移転 |
| 明細数量が学年組の合計と違う | 明細数量と学年・組の内訳の照合 | 学年組の追加・削除・変更 |
| メーカーへの発注数と学校注文数が不一致 | 行単位に未手配数を表示、超過は例外扱いと理由記録 | 分割発注、発注キャンセル |
| 出荷が一部だけ、または後で訂正される | 出荷明細と発注明細を紐付け、**残数量**を更新。訂正は履歴に残す | 分納、欠品、過剰出荷、同一通知の二重取込 |
| 納品数を上回る請求 | \`invoice_sources\` の割当数で上限を確認。例外請求は理由と承認が必要 | 二重請求、分割請求、送料や調整額 |
| 金額・税率が変わる | 明細ごとに税区分と確定時点の単価を保持。端数処理方法は決定が必要 | 税率混在、値引・返品、丸め |
| 原本のPDFが変わる・紛失する | 発行時のPDF原本・ハッシュ・版を別保存し、バックアップ＋復元試験 | 再発行、破損、旧版復元 |
| 権限外の学校案件にアクセス | リクエストごとにサーバー側で学校・担当・本部権限を照合 | 他担当のURL直接アクセス、改ざんされたID |

## フェーズBで相談して決定すべき項目

| ID | 論点 | 仮案（未確定） |
|---|---|---|
| B-01 | 「1案件」の区切り | **学校からの依頼単位**。同じ学校でも別の依頼は別案件とする |
| B-02 | 見積から注文へ進む際の価格・数量 | 見積時点をコピーして学校の最終確認を取り、注文番号を独立採番 |
| B-03 | 受注の確定権限 | 学校からの依頼入力≠正式受付。本部または認められた担当者が最終確認 |
| B-04 | メーカー発注の送信方法 | 当初は**PDF・印刷等で確認して既存手段で送信**し、システムは送信済み記録を管理 |
| B-05 | 納品・請求に送料、値引、返品、補充をどう反映するか | 通常明細と調整明細を分離、訂正理由は必須 |
| B-06 | 帳票番号、税の端数処理、改訂・取り消し | 本部の運用と帳票様式に合わせて具体例で決める |
| B-07 | 学校担当者名の保存期間・共用端末対応 | 必要最小限、権限ごとの閲覧、保持期間・自動ログアウトを定める |
| B-08 | 認証・DB・ファイルのXserver構成 | サーバー契約と現行仕様、管理権限を確認後に**ステージングで**採用判断 |

## フェーズBの受入条件

1. **学校Web・FAX・電話・訪問**を、同じ案件台帳につなげられるモデルである。
2. 見積番号と注文番号は独立で、注文の二重確定を防ぐ設計がある。
3. 学年組内訳と商品数量、出荷・納品・請求の割当数量を照合できる。
4. 確定帳票の宛先・価格・内容が、マスター編集で不意に変わらない。
5. 担当営業と本部の権限制御をサーバー側で検査する前提である。
6. **現行画面を変更せず**設計をレビューし、保留事項をユーザーと決定する。

現時点では設計案のみ。MySQL等の実テーブル作成、PHPの実装、Xserverへの接続・公開、実データの登録は**未実施**。
